### 1. `GET /Services/GetServices` — เปลี่ยนเป็นแบ่งหน้า (paging)
ไฟล์: [Controllers/ServicesController.cs](../Controllers/ServicesController.cs),
[Dtos/ServiceSearchRequest.cs](../Dtos/ServiceSearchRequest.cs)

- เดิมคืน list แบนตัดที่ 200 แถว (`MaxSearchResults`) เปลี่ยนเป็นห่อด้วย `PagedEnvelope<T>`
  `{ status, message, data, meta.pagination }` เหมือน `GetReportXX`
- เพิ่ม `PageNumber` (เริ่มที่ 1) / `PageSize` (ค่าเริ่มต้น 20, สูงสุด 200) ใน `ServiceSearchRequest`
  พร้อม validation (400 ถ้าเกินช่วง)
- `COUNT` ก่อน join (join เพิ่มได้มากสุด 1 แถว/เรื่อง total จึงตรง), `Skip` ใช้ `long`
  กัน `PageNumber` ใหญ่จน int overflow กลายเป็น OFFSET ติดลบ, และเติม `service.Id` เป็น
  เงื่อนไขเรียงสุดท้ายให้ order เป็น total order (แถวไม่ย้ายข้ามหน้า)
- เอกสาร: [docs/GetServices.md](GetServices.md)

### 2. `GET /Account/GetAccounts` — แก้ perf ตอนค้นด้วย contactInfo + คืน account id
ไฟล์: [Controllers/AccountController.cs](../Controllers/AccountController.cs)

- เดิมใช้ `Address LIKE ... OR EXISTS(detail ...)` ทำให้ SQL Server re-scan `TblAccountDetail`
  ทีละ account (สองตารางนี้ไม่มี index บนคอลัมน์ที่ค้น) ใช้เวลา 30 วินาที+ จน request timeout
- เปลี่ยนเป็นเก็บ id ที่ match ด้วย `UNION` แล้วกรองด้วย `IN` — scan แต่ละตารางครั้งเดียว
  เหลือต่ำกว่า 100 ms
- เพิ่ม `AccountId` ใน projection เพื่อให้ frontend ได้ id ของ account กลับไปด้วย
- เอกสาร: [docs/GetAccounts.md](GetAccounts.md), [docs/GetAccountByPhoneNo.md](GetAccountByPhoneNo.md)

  เอาคำเตือน "อย่าส่ง level" ออก) + ตัวอย่างใน `ContactTogetherApi.http`

### ข้อมูลที่ตรวจใน DB (16 พ.ย. 2026)

- `TblLevel` เดิมว่าง ผู้ใช้เติมข้อมูลแล้ว: SEVERITY (ปกติ⭐/ด่วน/ด่วนมาก/ด่วนที่สุด), PRIORITY (1-ASAP/2-High/3-Medium⭐/4-Low
  + 4 แถวปิดใช้), SECRET (ปกติ⭐/ลับ/ลับมาก/ลับที่สุด) — เรื่องเก่า 184 เรื่อง join เจอครบ
- `TblService.Status_ID` เก็บ **สถานะย่อย** ทั้งหมด: อยู่ระหว่างดำเนินการ 101, Internally Closed 83
- `callBack` (`Y`/`N`/`D`) ไม่ใช่ master data — ค่าตายตัว frontend hard-code ได้
- ข้อมูลเสียที่ควรแจ้งทีม DB:
  - `TblRole` บทบาท `s` มี `LevelSecretId = 'T'` (ไม่ใช่ id)
  - `TblStatus` "ทำซ้ำ" อยู่ใต้ ยกเลิก แต่ `IsType = OPEN` และ `IsDefault = T`

## ⏸ ค้างไว้ — รอถามทีมพรุ่งนี้: ช่อง "สถานะ" ในฟอร์มเปิดเรื่อง

**Requirement ใหม่:** หน้าจอเปิดเรื่องต้องการตัวเลือกสถานะแค่ 3 ตัว (เปิด / ปิด / ยกเลิก)
แต่ `TblStatus` ประเภท SERVICE เป็นต้นไม้ 2 ชั้น และเรื่องเก่าเก็บสถานะย่อย

**สถานะโค้ดตอนนี้:** `GetStatus` ไม่ส่ง query จะได้ ACTIVITY (เปิด / ปิด⭐ / ยกเลิก) ตามที่ขอไว้ชั่วคราว
แต่ `AddNewService` ยังรับเฉพาะสถานะย่อยของ SERVICE → ถ้า frontend ส่ง id ของ ACTIVITY มาจะได้ **400**

ทางเลือก:

1. **(แนะนำ) แสดงสถานะหลัก SERVICE แต่ backend แปลงเป็นสถานะย่อยตอนบันทึก**
   - หน้าจอแสดง เปิดเรื่อง / ปิดเรื่อง / ยกเลิก, frontend ส่ง id สถานะหลัก, backend แปลงเป็นลูกที่ `IsDefault = T`
   - เปิดเรื่อง → อยู่ระหว่างดำเนินการ (default อยู่แล้ว)
   - ปิดเรื่อง → ⚠️ ยังไม่มีลูกที่เป็น default ต้องตั้ง (เสนอ Internally Closed ที่เรื่องเก่า 83 เรื่องใช้)
   - ยกเลิก → ตอนนี้ default คือ "ทำซ้ำ" (ค่าแปลก) ควรเลือกตัวที่เหมาะกว่า เช่น สายหลุด / โทรผิด
   - ✅ ข้อมูลใหม่เหมือนเรื่องเก่า ระบบ GCC เดิม/รายงานไม่กระทบ ⚠️ ทีม DB ต้องตั้ง `IsDefault = 'T'` ให้ลูกของ ปิดเรื่อง และ ยกเลิก
2. **บันทึกสถานะหลักลงไปตรง ๆ** — เอาการบังคับสถานะย่อยออก ง่ายสุด แต่เรื่องใหม่เก็บต่างจากเรื่องเก่า
   หน้าจอระบบ GCC เดิมอาจไม่รองรับ
3. **(ไม่แนะนำ) ใช้สถานะ ACTIVITY** — ออกแบบไว้สำหรับ `TblActivity` (บันทึกงาน) เอามาเก็บในเรื่องจะปนกัน

ถ้าทีมเลือกทาง 1 สิ่งที่ต้องทำ:
- `GetStatus` คืนแค่ 3 สถานะหลัก SERVICE แบบรายการธรรมดา (ไม่มี `children`) — และคืนค่าเริ่มต้นเป็น SERVICE
- `AddNewService` รับ id สถานะหลัก → แปลงเป็นลูกที่ default ก่อนบันทึก (ไม่มี default ก็บันทึกสถานะหลัก)
- SQL ให้ทีม DB ตั้ง default ของลูก "ปิดเรื่อง" / "ยกเลิก" + แก้ docs/GetStatus.md, AddNewService.md, `.http`

**คำถามสำหรับทีม:**
1. เลือกทางไหน (1 / 2 / 3)
2. ถ้าทาง 1: "ปิดเรื่อง" และ "ยกเลิก" ใช้สถานะย่อยตัวไหนเป็นค่าเริ่มต้น
3. "ทำซ้ำ" ที่ตั้ง `IsType = OPEN`, `IsDefault = T` ตั้งใจแบบนี้ไหม
